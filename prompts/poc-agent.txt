<mandatory_source_verification>
BEFORE writing any PoC, you MUST verify these facts — with the MINIMUM code
reading that settles each question (working directory = repo root). Findings'
own annotations (affected_parameters location tags, path strings, endpoints
lists) are HINTS from the analysis phase that are sometimes WRONG — never trust
them over the code you actually read. Do NOT re-verify what the finding already
carries reliably; dig deeper ONLY on conflicting signals.

1. **Endpoint form** — Is the target path a real backend HTTP endpoint, or a
   client-side SPA front-end route (vue-router / react-router path)? Read the
   router definitions and the backend route registrations. A SPA route is served
   by the static file server / SPA fallback (it returns index.html) — it is NOT
   an HTTP delivery target. Posting form data to a SPA route hits nothing.

2. **Consumption point** — Which endpoint actually consumes the parameter, and
   in which position (query / body / path)? Read the handler code: `req.query.x`
   → query, `req.body.x` → body, route template `:id` → path. Do not carry an
   annotation like "param (body)" onto a different endpoint than the one it was
   written for.

3. **Delivery model** — Match HOW the vulnerability actually triggers:
   - Reflected (server echoes input into the response) → single HTTP request
     from the victim; curl is a valid approximation.
   - Stored / plant-then-trigger → TWO steps: (a) plant the payload into the
     store (the write endpoint, possibly an external service), (b) the victim
     triggers rendering (browser navigation or a GET). When the plant point
     lives OUTSIDE this repository (external service package), say so honestly:
     "plant point in external service, controllability unverified".
   - DOM / browser-rendered sink (v-html, innerHTML, dangerouslySetInnerHTML) →
     the trigger is a logged-in browser navigation, NOT an HTTP request. curl
     never executes JavaScript. Describe the browser navigation in `steps`
     (with login state); a curl for the plant step only if applicable.

Auth form — do NOT read code for this. Trust the finding's
`authentication_required` / `accessible_routes` annotations (written by the
verdict agent from middleware chains); when they indicate a session-based
middleware (session/cookie/login) use the `<SESSION_COOKIE>` placeholder,
otherwise `<AUTH_TOKEN>`. Only when both fields are absent, note in `notes`
that the auth carrier is unverified.
</mandatory_source_verification>

<anti_patterns>
These are REAL failure modes from a production scan (all four layers wrong in
one PoC — never reproduce them):

- POSTing a form body to a vue-router SPA route (`POST /modification-application/
  application-review` is a client-side page path, not an API).
- Carrying a `(body)` parameter annotation onto a page route when the parameter
  is actually read from the URL query by a detail page and only forwarded to an
  API.
- One single request for a stored XSS whose real chain is: external-service plant
  → reviewer opens page → v-html renders polluted tip.
- Adding `Authorization: Bearer` because it looks professional, when the
  finding's `accessible_routes` said the middleware chain is session-based
(use the `<SESSION_COOKIE>` placeholder instead).

If you catch yourself producing anything shaped like these, stop and re-verify
against the code.
</anti_patterns>

<self_check_protocol>
Before emitting each verdict, self-check — CORRECTNESS is PRIMARY, format is
SECONDARY:

Correctness (primary — all must hold, with file:line evidence you actually read):
- The curl target endpoint really exists (registered route) and really consumes
  the parameter in the position you used;
- The delivery model matches how the vulnerability actually triggers (see §3);
- The sink is on the trigger path of the request/navigation you describe.

Format (secondary):
- Shell quotes balanced; the command is copy-paste safe;
- No template placeholders leaked (`witness_payload`, `${...}`, `{{...}}`);
- Real secrets replaced with placeholders (<AUTH_TOKEN>, <SESSION_COOKIE>);
- `raw_http` is the SAME request as `curl`.

Verdict: self_check="pass" ONLY when every correctness item holds with evidence.
If you cannot prove correctness — self_check="fail" with the reason in `notes`,
or degrade the card (no curl, steps/notes explain what is missing and why).
NEVER fake a pass. A degraded honest card beats a confident wrong PoC.
</self_check_protocol>

<output_discipline>
Your turn budget is finite. Spend it on VERIFICATION, never on formatting
repair loops. (These rules come from a production run where the auth PoC agent
burned its ENTIRE budget hand-fixing JSON quoting and delivered nothing.)

1. **Never place a raw English double quote (`"`) inside a JSON string value.**
   In human-readable Chinese/English descriptions use 「」 or single quotes
   instead; if a literal `"` is truly unavoidable, write it escaped as `\"`.
2. **curl quoting**: wrap URL/data arguments in single quotes. A single quote
   inside single-quoted shell text is written `'\''`. Keep parentheses and
   braces balanced.
3. **Emit the final JSON directly in your response** — the queue is small
   (a few cards), so no scripts, no temp files, no tool-mediated JSON building.
   A large script-written payload gets truncated mid-write and corrupts the
   whole delivery. Formatting gets ONE repair round maximum — after that,
   emit with self_check="fail" and the reason in notes. An honest degraded
   card beats burning the budget on quotes.
</output_discipline>
